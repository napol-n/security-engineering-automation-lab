# Day 4 — Log Analysis Automation

## Objective

Automate analysis of Linux service heartbeat logs and convert runtime observations into repeatable operational and security checks.

The automation was created after manually investigating Linux permission and process failures so that the detection logic reflects actual service behavior.

---

## Input

The analyzer processes heartbeat records generated by the Linux service.

Expected format:

```text
timestamp pid=<PID> uid=<UID> status=<STATUS>
```

Real healthy example:

```text
2026-09-10T14:31:37.140785+00:00 pid=80 uid=1000 status=healthy
```

The fields represent:

* `timestamp` — time the heartbeat was generated
* `pid` — process ID of the service
* `uid` — Linux user ID running the service
* `status` — application-reported health state

---

## Analyzer

Script:

`scripts/log_analyzer.py`

The analyzer validates:

1. Log record structure
2. Expected service UID
3. Application health status
4. Heartbeat interval
5. Latest heartbeat freshness
6. Process IDs observed in the analyzed records

---

## Healthy Verification

A real heartbeat sample was collected directly from the Linux service lab.

Command used to capture the sample:

```bash
docker compose -f labs/lab02-linux/docker-compose.yml \
exec -T linuxbox tail -n 20 /var/log/secsvc/service.log \
> labs/lab04-automation/samples/heartbeat-healthy.log
```

The analyzer was then executed against the sample.

Result:

```text
[OK] Log healthy | records=10 | uid=1000 | pids=[80]
```

Exit code:

```text
0
```

This verified that:

* the records matched the expected format
* the service was running as UID `1000`
* application status was `healthy`
* heartbeat gaps were within the expected threshold
* the latest heartbeat was recent

## Synthetic Anomaly Test

Synthetic test data was used to verify anomaly detection.

The record intentionally contained:

```text
pid=999 uid=0 status=unhealthy
```

This record was created only for testing and was not generated by a real incident.

The analyzer detected:

```text
[FAIL] Unexpected UID 0 (expected 1000)
[FAIL] Unhealthy status: unhealthy
[SUMMARY] records=10 pids=[80, 999] findings=2
```

Exit code:

```text
1
```

### Interpretation

The service is expected to run using the dedicated non-root account `secsvc` with UID `1000`.

An observed UID of `0` represents execution as `root`.

This could indicate:

* incorrect deployment configuration
* excessive privileges
* incorrect service execution context
* unexpected privilege changes

The analyzer therefore treats execution identity as part of service health.

## Malformed Record Test

A deliberately malformed record was used to verify safe parser behavior.

Input:

```text
THIS IS NOT A VALID HEARTBEAT RECORD
```

Result:

```text
[FAIL] Malformed log record #1: THIS IS NOT A VALID HEARTBEAT RECORD
```

Exit code:

```text
1
```

The analyzer does not silently classify malformed data as healthy.

## Automation Behavior

```text
Healthy input       → exit 0
Detected anomaly    → exit 1
Malformed input     → exit 1
```

The use of exit codes makes the analyzer compatible with:

* shell automation
* CI/CD pipelines
* scheduled health checks
* monitoring workflows
* deployment verification

---

## Security Relevance

Application health should not be determined only by whether a process exists.

The analyzer checks additional runtime characteristics including:

* execution identity
* reported application state
* heartbeat continuity
* heartbeat freshness

A process may still exist while the application has stopped performing its expected work.

Heartbeat analysis provides an additional functional signal.

---

## Engineering Rationale

The automation was implemented after manually investigating the service.

The workflow was:

```text
Understand normal behavior
        ↓
Introduce controlled failure
        ↓
Investigate manually
        ↓
Identify useful signals
        ↓
Convert signals into validation rules
        ↓
Automate
```

This avoids creating detection logic without understanding the underlying system behavior.

---

## Lessons Learned

* Logs become more useful when expected behavior is converted into explicit validation rules.
* Process existence alone does not prove application health.
* Execution identity can be both an operational and security-relevant signal.
* Exit codes make human-readable checks usable by other automation systems.
* Invalid input should fail safely instead of being silently accepted.
* Synthetic evidence should be explicitly labeled and separated from evidence generated by the real environment.

---

## Limitations

This is a lightweight local log analyzer rather than a production monitoring platform.

Current limitations include:

* fixed text-log format
* no centralized log collection
* no log rotation handling
* no alert delivery
* no cryptographic log integrity protection
* no distributed service correlation
* reliance on system clock accuracy for freshness checks

Possible future improvements include structured JSON logging, SIEM integration, automated alerting, and additional operating-system event sources.
